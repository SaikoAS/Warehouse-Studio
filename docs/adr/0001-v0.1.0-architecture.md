# ADR 0001: v0.1.0 architecture and acceptance

Status: Accepted for v0.1.0 planning. The maintainer's scope and stack decision is recorded in [Issue #2](https://github.com/SaikoAS/Warehouse-Studio/issues/2).

**v0.2.0 update:** The maintainer-approved scope in [Issue #20](https://github.com/SaikoAS/Warehouse-Studio/issues/20) and window lifecycle in [Issue #21](https://github.com/SaikoAS/Warehouse-Studio/issues/21) supersede this ADR's parallel-project window decision and the corresponding simultaneous-project acceptance scenarios below. v0.2.0 supports one active project, with separate module windows; opening another project requires closing the active project first. Issue #21 specifies the replacement isolation and lifecycle checks. The remaining v0.1.0 decisions and historical acceptance scenarios below are retained for context.

## Decision and scope

The first usable workflow is to choose or create a project, import one local CSV per preparation workflow, configure ordered preparation steps, and view the saved result. Warehouse Studio owns its application and project format. OpenSlotting informed the local startup and separate-window patterns. Running Warehouse Studio requires only its own distribution and project files, together with the approved Python installation and Edge.

The 2D warehouse editor, geometry, occupancy views and SVG plan rendering belong to future scope. CSV export, source replacement, multi-source transformations and detailed project backup/restore are separate decisions.

## Local runtime and project boundaries

| Boundary | Agreed design and rationale |
| --- | --- |
| Distribution and launch | The user extracts a ZIP into a writable local folder and double-clicks a Windows start script. The script starts the local Python service and opens Edge. The ZIP contains the prebuilt interface, service and scripts. The runtime works offline as a standard user, without a dedicated executable, system installation, dependency downloads or Node/npm. A separately invoked setup script can add a current-user shortcut. Removing that shortcut preserves program files and project data. [Runtime](https://github.com/SaikoAS/Warehouse-Studio/issues/5) · [Packaged acceptance](https://github.com/SaikoAS/Warehouse-Studio/issues/8) |
| Interface and service | TypeScript and React implement the launcher, preparation editor and source/result views. TypeScript makes the project and preparation contracts explicit. Vite produces static assets for the ZIP. Python serves those assets and the app's local operations at `127.0.0.1`, owns data preparation and writes project data. Edge uses the loopback app URL. The portable `file:///index.html` entry point is outside this distribution. CSVs and databases are outside the static asset surface. [Runtime](https://github.com/SaikoAS/Warehouse-Studio/issues/5) |
| Project selection and storage | The launcher reads only the metadata needed to list projects in a user-selected local folder. It creates one versioned SQLite database per project in that folder, separate from the extracted app. Python owns persistence. SQLite provides transactional saves inside the existing runtime and keeps project data independent of Edge's browser storage. [Project launcher](https://github.com/SaikoAS/Warehouse-Studio/issues/6) |
| Parallel windows | Opening a project creates a dedicated Edge app window and leaves the launcher usable. Several different projects can be open at once. Reads and writes are bound to the project that opened the window. Opening, saving or closing project B leaves project A's state, file and window intact. Each project loads its data when opened. [Project launcher](https://github.com/SaikoAS/Warehouse-Studio/issues/6) |

## CSV preparation and saved results

1. **Source.** Import a local UTF-8 CSV with semicolon delimiters and user-defined column names into the open project. Retain the source bytes exactly. Display original data read-only and retain the source location for errors. Identifiers such as `0007` stay text.
2. **Steps and preview.** The user adds, edits, reorders or removes steps for column renaming, row filtering or type conversion. The first types are text and decimal, with an explicit locale for decimal conversion. Selecting a step shows a read-only preview through that step. Python evaluates preview and full processing with the same rules.
3. **Apply and reopen.** The user's explicit **Apply** publishes a valid result to that project's SQLite file, separate from the original bytes and step definition. An invalid conversion identifies the original line and column. A failed Apply leaves the last valid result available. On reopening, the saved steps and result are available. Replaying the same valid steps on the same source produces the same result.

The project keeps both the original source and the applied result so the user can inspect what changed and reproduce the result. The exact CSV size supported by the first build is tracked in [Issue #7](https://github.com/SaikoAS/Warehouse-Studio/issues/7). The supported Windows Python version and `sqlite3` availability are tracked in [Issue #5](https://github.com/SaikoAS/Warehouse-Studio/issues/5). The Python 3.11+ minimum for the existing repository checks is a separate tooling requirement.

## Planned acceptance

| Boundary | Automated checks planned | Windows/Edge acceptance planned |
| --- | --- | --- |
| Build and service ([#5](https://github.com/SaikoAS/Warehouse-Studio/issues/5)) | Build with the lockfile, type-check the UI, smoke-test loopback startup and static asset handling. Check prerequisite or port errors where practical. Keep the existing repository checks. | Start the built app in Edge via the Windows script on the intended Python installation. Record the Python version and verify `sqlite3` is available. |
| Project and window isolation ([#6](https://github.com/SaikoAS/Warehouse-Studio/issues/6)) | Verify project creation and reopen, visibility limited to the chosen folder, and reads/writes isolated to the originating database. Cover missing or unreadable projects without losing the launcher. | Choose a data folder, create project B alongside synthetic project A, and open both in separate Edge app windows. Save and close B, then confirm A and the launcher remain usable and A's saved data is unchanged. Choose a different data folder and confirm the launcher list changes. |
| CSV and result ([#7](https://github.com/SaikoAS/Warehouse-Studio/issues/7)) | Use the synthetic success/error fixtures to verify step order, leading zeros, exact decimals with a decimal comma, preview/result agreement, source bytes, original error line/column, reopen/replay and rollback. Verify the documented initial file-size target with generated data. | Import the fixture, rename a column, filter rows, and convert the quantity column. Inspect the selected-step previews and saved result. Reopen the project, replay the steps, then exercise a failing conversion and confirm the last valid result remains visible. |
| ZIP and offline use ([#8](https://github.com/SaikoAS/Warehouse-Studio/issues/8)) | Verify the archive contains the required built assets, service and scripts. Record the candidate commit and check results. | On the intended Windows device, extract that ZIP as a standard user and run it with the network disconnected. Verify direct launch and optional shortcut creation/removal. Complete the data flow in one project with a second project open. Record the tested Windows, Edge and Python versions and any acceptance gaps. |

The CSV implementation PR includes a valid fixture and a separate invalid-conversion fixture, with expected prepared rows and the expected error location. Use entirely fictional identifiers and values. A rollback check can first apply the invalid-conversion fixture as text in its own workflow, then apply the decimal conversion that fails. This exercises failure against a previous valid result without changing the imported file.

Passing repository checks validates this documentation. Passing future application checks and observing the packaged offline flow provide separate evidence for product acceptance.
